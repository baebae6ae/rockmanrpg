# 록맨 RPG — 설계 문서

> 상태: **초안 (v0.1)** — 논의를 거쳐 계속 갱신됨. 확정된 결정과 미결 사항을 구분해 표기한다.

---

## 1. 프로젝트 개요

전 록맨 시리즈를 아우르는 **크로스오버 육성 액션 RPG**.
메이플스토리식 횡스크롤 사냥·성장 구조 위에, 록맨 시리즈의 캐릭터·특수무기·약점 상성 시스템을 얹는다.

### 1.1 확정 사항

| 항목 | 결정 |
|---|---|
| 장르 | 횡스크롤 액션 육성 RPG (메이플스토리형) |
| 멀티플레이 | **없음.** 싱글플레이 전용 (구조는 열어두되 구현하지 않음) |
| 기준 화풍 | 록맨 X4 (PS1, 1997) — 내부 해상도 320×240 |
| 화풍 정책 | **전 시리즈 혼용.** NES·SNES·GBA·PS1 도트를 그대로 섞는다 (크로스오버 컨셉의 시각적 표현) |
| 플레이어블 | 원작에 플레이어블 스프라이트가 존재하는 주역 **7명 + 액셀** |
| 적 | 이레귤러·로봇마스터 200여 명 + 잡몹 전체. 원작 스프라이트 그대로 활용 |
| 엔진 | **TypeScript + PixiJS** (웹) |
| 개발 환경 | 주로 모바일. 빌드를 Artifact로 퍼블리시해 폰에서 직접 플레이하며 확인한다 |
| 에셋 관리 | 정규화된 스프라이트는 **저장소에 커밋**한다 (CI 빌드에 필요). 원본 리핑 시트와 생성물은 제외 |
| 초기 아트 | 규격에 맞는 **임시 도트를 스크립트로 생성**. 진짜 스프라이트는 동일 규격으로 파일만 교체 |
| 배포 | 정적 웹앱. GitHub Pages(정식) + Artifact(개발 중 즉시 확인) |

### 1.2 설계 원칙

1. **콘텐츠는 코드가 아니라 데이터다.** 캐릭터·스킬·적·보스 패턴 추가에 코드 수정이 필요하면 설계가 틀린 것이다.
2. **코드는 에셋 경로만 안다.** 스프라이트 교체가 경로 변경만으로 끝나야 한다.
3. **스프라이트 규격을 먼저 고정한다.** 리핑 시트의 불규칙성(가변 프레임 크기·정렬)은 임포트 시점에 흡수하고, 런타임은 고정 캔버스 균일 격자만 다룬다. 임시 도트도 같은 규격으로 생성하므로 교체가 파일 교체만으로 끝난다.
4. **물량은 티어로 나눈다.** 전부를 같은 품질로 만들려 하면 아무것도 완성되지 않는다.
5. **가속 곡선을 넣지 않는다.** 록맨 시리즈의 조작감은 입력이 곧 속도라는 데서 나온다. 방향키를 누르면 즉시 최고 속도, 떼면 즉시 정지, 공중에서도 방향 전환이 즉시 된다. 가속·감속 보간을 넣으면 미끄러지는 느낌이 되어 시리즈 특유의 정확한 조작감이 사라진다.
6. **지형은 배경과 명확히 구분되어야 한다.** 밟을 수 있는 것과 없는 것이 한눈에 갈리지 않으면 플랫포머로서 성립하지 않는다. 지형은 밝게, 배경은 어둡고 낮은 대비로.

## 2. 렌더링 규격

| 항목 | 값 |
|---|---|
| 내부 렌더 해상도 | 320×240 |
| 화면 출력 | 정수배 스케일링만 (×2 = 640×480, ×3 = 960×720, ×4 = 1280×960) |
| 스프라이트 스케일 | **정수배만 허용.** 비정수 스케일 금지 (픽셀 뭉개짐) |
| 캐릭터 크기 | 원본 그대로. X4 캐릭터 ≈ 40px, NES 캐릭터 ≈ 24px — 차이를 그대로 둔다 |
| 히트박스 | **스프라이트 크기와 분리.** 데이터로 별도 정의해 밸런스를 맞춘다 |
| 프레임 캔버스 | 캐릭터별 **고정 크기** (기본 64×64). 발바닥을 하단 중앙에 정렬 |

### 2.1 혼용 화풍 대응

크기·색수·프레임 수가 캐릭터마다 다르다. 이 불규칙성은 **임포트 시점에 흡수하고**, 런타임은 정규화된 균일 격자만 다룬다.

**임포터가 흡수하는 것**

- 원본 리핑 시트의 불규칙한 프레임 크기·위치 → 고정 캔버스로 정규화
- 프레임마다 다른 정렬 기준 → 발바닥 하단 중앙으로 통일

**런타임이 가정하지 않는 것**

- 고정 프레임 수 (NES 달리기 3프레임 vs X4 달리기 11프레임+)
- 캐릭터 간 동일한 캔버스 크기 (캐릭터마다 다를 수 있음)
- 고정 팔레트 깊이
- 스프라이트 크기와 히트박스의 일치

## 3. 기술 스택

**TypeScript + PixiJS (웹)**

### 3.1 선정 근거

개발이 주로 **모바일에서 진행된다**는 제약이 스택 선택을 지배한다.

- **결과를 즉시 확인할 수 있다.** 빌드를 단일 HTML로 묶어 Artifact로 퍼블리시하면, 폰에서 바로 플레이해볼 수 있다. "만든다 → 올린다 → 해본다 → 고친다"의 순환이 성립한다.
- **에디터가 필요 없다.** Godot을 검토했으나 최대 장점인 내장 맵/씬 에디터를 모바일에서 열 수 없어 근거가 성립하지 않는다. 헤드리스로만 돌리면 개발자와 제작자 양쪽 모두 화면을 보지 못한 채 작업하게 된다.
- **데이터 주도 설계와 JSON이 한 몸이다.** 스키마·검증·임포트 파이프라인이 자연스럽다.
- **PixiJS는 2D 스프라이트 배칭에 특화**되어 있고, 이 규모(동시 수백 스프라이트)에서 성능 여유가 충분하다.
- 팔레트 스왑은 프래그먼트 셰이더로 처리한다.

**포기하는 것:** 내장 맵 에디터. 맵은 JSON 데이터로 기술하며, 필요해지면 브라우저 기반 맵 에디터를 별도로 만든다 (그편이 어느 기기에서든 열린다는 이점도 있다).

### 3.2 렌더링·입력

- 320×240 렌더 타깃에 그린 뒤 정수배로 확대. `NEAREST` 필터 고정
- **입력은 키보드와 터치 양쪽을 지원한다.** 모바일이 주 확인 수단이므로 가상 D-패드 + 버튼이 필수
- Artifact는 외부 요청이 차단되므로, 퍼블리시용 빌드는 **모든 에셋을 인라인한 단일 HTML**로 만든다

### 3.3 도구 체인

| 도구 | 용도 | 실행 위치 |
|---|---|---|
| Vite | 개발 서버, 번들, 단일 HTML 빌드 | 컨테이너 |
| `tools/detect_frames.py` | 리핑 시트에서 프레임 자동 검출·정규화 (Pillow) | 컨테이너 / PC |
| `tools/gen-placeholder.ts` | 규격에 맞는 임시 도트 생성. **빌드 시 자동 실행** | 컨테이너 / CI |
| `tools/validate-data.ts` | 데이터 스키마 검증 | 컨테이너 / CI |
| **Aseprite** | 프레임 묶기·태그 부여 (자동 검출 후 보정) | **PC 세션** |

```
│   ├── world/                 # 맵, 포탈, 스폰 테이블
│   └── ui/                    # HUD, 인벤토리, 스킬창, 도감
├── data/                      # 게임 데이터 (버전 관리 O)
│   ├── characters/            # 플레이어블 캐릭터 정의
│   ├── skills/                # 스킬·특수무기 정의
│   ├── enemies/               # 잡몹·보스 정의
│   ├── patterns/              # 보스 행동 패턴
│   ├── items/                 # 장비, 소모품, 배틀칩
│   ├── elements.json          # 속성·약점 상성표
│   └── maps/                  # 맵 메타데이터, 스폰 테이블
├── assets/
│   ├── sprites/               # 정규화된 스프라이트 (버전 관리 O — 배포에 포함)
│   ├── raw/                   # 원본 리핑 시트 (버전 관리 X — 중간 산물, 재수집 가능)

├── tools/                     # 프레임 검출, 임시 도트 생성, 데이터 검증
└── .github/workflows/
    └── deploy.yml             # Pages 자동 빌드·배포
```

- `assets/sprites/`는 **커밋한다.** CI가 빌드할 때 리포에 없으면 배포된 게임이 비어버린다.
- `assets/raw/`는 임포트 전 중간 산물이라 커밋하지 않는다. 필요하면 다시 받으면 된다.
- `assets/generated/`는 빌드 시 `tools/gen-placeholder.ts`가 재생성하므로 커밋하지 않는다.

## 5. 스프라이트 시트 규격

> **에셋 수집 시 이 절을 기준으로 삼는다.**

### 5.1 파이프라인

```
원본 리핑 시트                     assets/raw/<id>.png
   │   (불규칙한 크기·위치, 메타데이터 없음)
   ├─ tools/detect_frames.py       프레임 경계 자동 검출 + 발바닥 정렬
   ├─ Aseprite                     프레임 묶기, 애니메이션 태그 부여   ← PC 세션
   ↓
정규화된 시트                      assets/sprites/<id>/
   │   (고정 캔버스 균일 격자)
   ↓
런타임 로더
```

임시 도트(`tools/gen_placeholder.py`)는 이 파이프라인의 **출력과 동일한 규격**으로 생성된다. 따라서 진짜 스프라이트가 준비되면 파일 교체만으로 대체된다.

### 5.2 정규화 규격

> **이 절이 임시 도트와 진짜 스프라이트의 호환을 보장한다.**

- 프레임은 **캐릭터별 고정 크기 캔버스**에 배치한다. 기본값 **64×64**, 대형 캐릭터는 캐릭터 단위로 키울 수 있다 (프레임 단위로는 불가).
- 정렬 기준은 **발바닥 하단 중앙** — 캔버스 좌표 `(w/2, h-1)`에 캐릭터의 접지점이 오도록 맞춘다.
- 시트는 **균일 격자**로 저장한다. 프레임별 피벗 데이터는 필요 없다.
- 여백만큼 텍스처를 더 쓰지만, 이 규모에서는 무시할 수 있는 비용이다.

정렬 기준을 통일하지 않으면 캐릭터가 애니메이션이 바뀔 때마다 위아래로 튄다. 대시 프레임은 넓고 점프 프레임은 높기 때문이다. 고정 캔버스는 이 문제를 임포트 시점에 한 번에 해결한다.

### 5.3 파일 배치 규칙

```
assets/sprites/characters/<character_id>/
    <character_id>.png        # 정규화된 균일 격자 시트
    <character_id>.json       # 캔버스 크기 + 애니메이션 태그 + 프레임 지속시간

assets/sprites/enemies/<enemy_id>/
    <enemy_id>.png
    <enemy_id>.json
```

`character_id` / `enemy_id`는 소문자 스네이크케이스 (`x`, `zero`, `rockman`, `blues`, `forte`, `vent`, `sting_chameleon`).

### 5.4 메타데이터 형식

```jsonc
{
  "canvas": { "w": 64, "h": 64 },
  "columns": 8,                     // 격자 열 수
  "tags": {
    "idle":      { "from": 0,  "to": 3,  "duration": 120, "loop": true },
    "run":       { "from": 4,  "to": 14, "duration": 60,  "loop": true },
    "jump_rise": { "from": 15, "to": 17, "duration": 80,  "loop": false }
  }
}
```

### 5.5 플레이어블 캐릭터 — 애니메이션 태그

**필수 (없으면 캐릭터가 동작하지 않음)**

| 태그 | 설명 |
|---|---|
| `idle` | 대기 |
| `run` | 이동 |
| `jump_rise` | 상승 |
| `jump_fall` | 하강 |
| `hurt` | 피격 |
| `death` | 폭발·소멸 |
| `attack_main` | 기본 공격 (버스터 사격 / 세이버 1타) |

**선택 (캐릭터별 능력에 따라)**

| 태그 | 해당 캐릭터 |
|---|---|
| `jump_land` | 전체 (착지 동작) |
| `dash`, `dash_start`, `dash_end` | X 시리즈 |
| `wall_slide`, `wall_kick` | X 시리즈, 제로 시리즈 |
| `ladder_idle`, `ladder_climb` | 클래식, X 시리즈 |
| `attack_run` | 이동 중 사격 (X 시리즈) |
| `attack_air` | 공중 공격 |
| `charge_loop`, `charge_release` | 차지 버스터 보유 캐릭터 |
| `attack_melee_1/2/3` | 제로 (세이버 3단 콤보) |
| `slide` | 클래식 계열 (아래 + 점프) |
| `spawn` | 워프 착지 연출 |
| `victory` | 스테이지 클리어 |

### 5.6 적·보스 — 애니메이션 태그

**잡몹 (필수 4종)**

`idle` / `move` / `hurt` / `death`

**보스 (추가)**

| 태그 | 설명 |
|---|---|
| `intro` | 등장 연출 |
| `telegraph` | 공격 예비동작 (패턴 가독성의 핵심) |
| `attack_1` ~ `attack_n` | 공격 모션 |
| `special` | 필살기 / 저체력 패턴 |
| `stun` | 그로기 (선택) |

> 보스는 이동 애니메이션이 필수가 아니다. 원작 보스 스프라이트를 거의 그대로 쓸 수 있는 이유.

## 6. 데이터 스키마

### 6.1 플레이어블 캐릭터

```jsonc
{
  "id": "x",
  "name": "엑스",
  "series": "x",                    // classic | x | zero | zx
  "sprite_scale": 1,                // 정수만
  "archetype": "buster",            // buster | saber | hybrid | ranged

  "hitbox": { "w": 16, "h": 32, "offset_x": 0, "offset_y": -16 },
  // 스프라이트 크기와 무관하게 캐릭터 간 균형을 맞춘 값

  "base_stats": { "hp": 100, "attack": 10, "defense": 5, "speed": 100, "jump": 220 },
  "growth":     { "hp": 8, "attack": 1.5, "defense": 0.8 },   // 레벨당 증가

  "movement": {
    "can_dash": true,
    "can_air_dash": true,
    "can_wall_kick": true,
    "can_double_jump": false,
    "can_climb_ladder": true,
    "can_slide": false
  },

  "equipment_slots": ["head", "body", "arm", "foot"],   // X 시리즈 아머 파츠
  "starting_skills": ["x_buster"],
  "skill_tree": "x_tree"
}
```

`movement` 플래그가 캐릭터 개성의 핵심이다. 클래식 록맨은 대시·벽차기가 없고 슬라이딩이 있으며, 엑스는 반대다. 이걸 코드 분기가 아니라 데이터로 두면 캐릭터 추가가 데이터 작업이 된다.

### 6.2 스킬 / 특수무기

```jsonc
{
  "id": "storm_tornado",
  "name": "스톰 토네이도",
  "element": "wind",
  "cost": 12,                       // 무기 에너지
  "cooldown": 0.8,
  "animation_tag": "attack_main",

  "unlock": { "source": "boss", "boss_id": "storm_eagleed" },
  // 록맨 원작 루프: 보스 격파 → 무기 획득

  "upgrade": {
    "max_level": 5,
    "sp_cost": [1, 2, 3, 5, 8],           // 레벨당 SP 소모
    "per_level": { "power": 0.15, "cost": -0.05 }
  },

  "effects": [
    { "type": "projectile", "sprite": "tornado", "speed": 180,
      "pierce": true, "lifetime": 1.2 },
    { "type": "damage", "power": 1.4, "scaling": "attack" },
    { "type": "knockback", "force": 60 }
  ]
}
```

**효과 프리미티브**를 조합해 스킬을 만든다. 새 스킬이 새 코드를 요구하지 않도록 프리미티브 세트를 먼저 잘 설계하는 것이 중요하다.

주요 프리미티브: `projectile`, `melee_hitbox`, `damage`, `heal`, `status`(빙결/감전/화상/독), `buff`, `knockback`, `dash_move`, `summon`, `area`, `pierce`, `multi_hit`, `charge_variant`

## 7. 보스 패턴 시스템

200여 보스의 행동을 코드로 짜면 유지가 불가능하다. **패턴을 데이터로 기술**한다.

### 7.1 행동 프리미티브

**이동**

| 프리미티브 | 파라미터 |
|---|---|
| `move_to` | 목표 위치, 속도 |
| `charge` | 방향, 속도, 거리 |
| `jump` | 높이, 거리 |
| `hop` | 반복 횟수, 높이 |
| `teleport` | 목표 위치, 페이드 시간 |
| `wall_bounce` | 속도, 반사 횟수 |
| `chase` | 지속 시간, 속도 |
| `hover` | 고도, 진폭 |

**공격**

| 프리미티브 | 파라미터 |
|---|---|
| `shoot` | 투사체 ID, 개수, 확산각, 간격 |
| `shoot_aimed` | 투사체 ID, 플레이어 조준 |
| `melee` | 히트박스, 지속 시간, 위력 |
| `laser` | 방향, 폭, 지속 시간, 예열 시간 |
| `area_attack` | 반경, 지연, 위력 |
| `summon` | 잡몹 ID, 수량, 위치 |
| `drop_object` | 오브젝트 ID, 개수 |

**제어**

| 프리미티브 | 파라미터 |
|---|---|
| `telegraph` | 애니메이션 태그, 지속 시간 |
| `wait` | 시간 |
| `face_player` | — |
| `loop` | 하위 시퀀스, 반복 횟수 |
| `random` | 하위 시퀀스 목록, 가중치 |
| `if_hp_below` | 비율, 분기 시퀀스 |
| `invulnerable` | on/off |

### 7.2 패턴 기술 예시

```jsonc
{
  "id": "boss_charger_a",
  "sequence": [
    { "op": "face_player" },
    { "op": "telegraph", "anim": "telegraph", "duration": 0.5 },
    { "op": "charge", "speed": "$charge_speed", "distance": 200 },
    { "op": "wait", "duration": 0.4 },
    { "op": "shoot_aimed", "projectile": "$projectile", "count": 3, "spread": 15 },
    { "op": "if_hp_below", "ratio": "$phase2_hp_ratio", "then": [
        { "op": "invulnerable", "value": true },
        { "op": "teleport", "target": "ceiling_center" },
        { "op": "area_attack", "radius": 80, "delay": 0.6 },
        { "op": "invulnerable", "value": false }
      ]
    },
    { "op": "loop", "count": -1 }
  ]
}
```

`$파라미터`는 적 정의의 `pattern_params`에서 주입된다. 같은 템플릿으로 수십 마리의 서로 다른 보스를 만들 수 있다.

### 7.3 보스 티어링

| 티어 | 규모 | 작업 방식 | 캐릭터당 비용 |
|---|---|---|---|
| **시그니처** | 20~30 | 전용 패턴 손수 설계 | 수 시간 |
| **일반 보스** | ~170 | 템플릿 8~10종 + 파라미터 교체 | 30분~1시간 |
| **잡몹** | 수백 | 템플릿 3~4종 + 스탯 표 | 수 분 |

이 구조에서 200명은 **아트 노동이 아니라 데이터 입력 작업**이 된다. 도트 실력이 필요 없고, 중단해도 손해가 없으며, 언제든 조금씩 늘릴 수 있다.

### 7.4 패턴 템플릿 목록

구현된 템플릿과 이를 쓰는 적:

| 템플릿 | 쓰는 적 | 성격 |
|---|---|---|
| `boss_charger_a` | 스팅 카멜리온, **스파크 맨드릴러** | 예비동작 → 돌진 → 조준 사격, 저체력 시 순간이동 탄막 |
| `boss_teleporter` | 부메르 쿠왕가 | 순간이동으로 위치를 바꾸며 사격·근접, 저체력 시 양쪽 지점 탄막 |
| `mob_patrol` | 워커 | 좌우 순찰 + 정지 사격 |
| `mob_hover` | 부유 드론 | 부유 이동 + 조준 사격 |

**같은 템플릿에 파라미터만 바꿔 다른 보스를 만드는 것이 실제로 성립한다.** 스팅 카멜리온과 스파크 맨드릴러는 `boss_charger_a` 하나를 공유하고 속도·위력·속성·본거지 좌표만 다르다.

앞으로 추가할 템플릿: `artillery` / `flyer` / `summoner` / `wall_crawler` / `laser_platform` / `multi_part`(대형 보스) / `stationary_turret`

## 8. 육성 시스템

록맨 원작 요소를 메이플식 구조에 대응시킨다.

| 시스템 | 록맨 대응 |
|---|---|
| 레벨 / 경험치 | 메카니로이드 소탕. 레벨업마다 **AP 3 · SP 1** |
| 능력치 분배 | AP 를 공격 / 방어 / 체력에 투자 |
| 스킬 트리 | **보스 드랍 + SP 강화** (§8.1) |
| 장비 4슬롯 | **X 시리즈 아머 파츠** (헤드 / 보디 / 암 / 풋) |
| 소모품 | 회복 캡슐·에너지 탱크 (마을 상점에서 구매) |
| 재화 | **볼트** — 적이 떨어뜨리고 상점에서 쓴다 |
| 맵 / 포탈 | **양방향 포탈로 이어진 세계** + 마을 (§8.2) |
| 도감 | 전 캐릭터·적 수집 요소 |
| 저장 | localStorage 자동 저장 (레벨·SP·무기 강화·장비) |

### 8.2 세계 구조 — 스테이지 선택이 아니다

**록맨의 스테이지 선택 화면을 넣으면 그 순간 육성 RPG 가 아니라 록맨이 된다.** 둘의 차이는 화면 하나가 아니라 세계를 대하는 방식이다.

| | 록맨 | 이 게임 (메이플형) |
|---|---|---|
| 맵의 성격 | 한 번 깨고 버리는 관문 | **계속 돌아오는 사냥터** |
| 이동 | 스테이지 선택 화면 | **포탈로 이어진 하나의 세계**, 왕복 가능 |
| 진행 기준 | 보스를 깼는가 | **내 레벨이 이 사냥터를 넘었는가** |
| 중심 공간 | 없음 | **마을** — 보급·회복·구매 |
| 재화 | 없음 | 볼트 → 물약·장비 구매 |

현재 세계:

```
헌터 베이스 (마을·안전지대)  ──[포탈]──  도시 외곽 (권장 Lv 1)  ──[포탈]──  폐기물 처리장 (권장 Lv 6)
   보급 담당(상점)                        잡몹 6                        잡몹 3 + 보스 3
```

- 포탈은 **양방향**이다. 사냥터에서 마을로 돌아와 보급하고 다시 나간다.
- 맵 진입 시 이름과 **권장 레벨**을 알린다. 어디로 갈지는 레벨이 정한다.
- 포탈·NPC·상점 품목은 전부 맵 데이터가 정한다. 새 사냥터를 붙이는 데 코드가 필요 없다.

### 8.3 사냥 루프

**육성 RPG 가 성립하려면 "사냥 → 성장 체감 → 더 사냥"이 돌아야 한다.** 액션 파트만 있으면 성장이 장식이 된다. 그래서 넷을 갖춘다.

| 요소 | 내용 | 없으면 |
|---|---|---|
| **적 리스폰** | 잡몹은 처치 후 6~7초 뒤 되살아난다 (`respawn`). 보스는 되살아나지 않는다 | 사냥터가 없다. 한 번 청소하면 끝 |
| **능력치가 데미지에 반영** | 공격력이 무기 위력에 더해진다 (`power + attack × 0.55`). 방어력은 받는 피해를 뺄셈으로 줄인다 | 레벨을 올려도 세지지 않는다 |
| **데미지 숫자** | 피격 지점에 뜬다. 약점은 크고 노랗게, 저항은 작고 흐리게 | 성장도 상성도 눈에 보이지 않는다 |
| **드랍** | 잡몹이 체력·무기 에너지 회복을 떨군다 (`drops`) | 사냥터에 머물 수 없다 |

### 8.4 무기 에너지

특수무기는 발동마다 에너지를 쓴다. 원작은 적을 잡아 회복 아이템을 얻지만, 적이 없는 보스 구역에서 에너지가 바닥나면 **특수무기가 영구히 잠겨 약점 시스템 자체가 성립하지 않는다.** 그래서 초당 1.5씩 자연 회복시킨다 (완충 약 19초). 연사는 막되 잠기지는 않는 선이다.

### 8.5 레벨 설계 규칙

플레이어블 중 절반이 벽타기를 못 한다(클래식 계열). 따라서:

- **벽타기 없이 지날 수 있는 경로가 항상 있어야 한다.** 벽타기는 지름길이나 수집품 접근 수단으로만 쓴다.
- **바닥까지 내려오는 벽으로 통로를 막지 않는다.** 한쪽만 막으면 들어가서 못 나오는 함정이 된다.

### 8.1 스킬 습득 구조

**보스 격파로 무기를 해금하고, SP를 투자해 무기별로 강화한다.**

- **해금** — 록맨 원작 루프 그대로. 보스를 잡으면 그 무기를 얻는다. 획득 자체에는 SP가 들지 않는다
- **강화** — 레벨업으로 얻은 SP를 개별 무기에 투자해 3~5단계까지 올린다. 위력 증가, 에너지 소모 감소 등
- **빌드** — SP가 유한하므로 "어떤 무기를 키울지"가 선택이 된다. 메이플식 빌드 재미를 확보하되, 잘못 찍어도 새 무기로 갈아탈 수 있어 부담이 적다

이 구조를 택한 실무적 이유: **스킬 트리를 캐릭터별로 손수 설계할 필요가 없다.** 트리가 무기 목록에서 자동으로 파생되므로, 캐릭터 8명 × 무기 200종 규모에서도 데이터만 채우면 된다. 분기형 트리는 로스터를 늘릴 때마다 설계 비용이 붙는다.

무기 상성(§6.4)이 이미 "어떤 보스에 어떤 무기를 쓸 것인가"라는 선택을 만들고 있으므로, 강화 투자는 그 위에 얹히는 두 번째 층이 된다.

## 9. 개발 순서

> **진행 상황**
>
> - **0차·1차 완료** — 이동·전투·육성·장비·보스 드랍이 모두 동작한다.
> - **2차 진행 중** — 플레이어블 5명(엑스·제로·록맨·블루스·포르테), 보스 3체, 특수무기 3종. 남은 것은 벤트/아일, 제로(제로 시리즈), 액셀.
> - **1.5차 준비 완료** — `tools/detect_frames.py` 작성됨. PC 세션에서 리핑 시트를 넣으면 바로 정규화된다.

### 0차 — 도구와 규격

에셋 없이 진행할 수 있는 단계. 모바일 환경에서 전부 가능하다.

- `tools/gen_placeholder.py` — §5.2 규격에 맞는 임시 도트 생성
- `tools/detect_frames.py` — 리핑 시트 프레임 자동 검출·정규화 (PC 세션에서 쓸 도구를 미리 만들어 둔다)
- `tools/validate_data.ts` — 데이터 스키마 검증
- Vite + PixiJS 프로젝트 골격, 단일 HTML 빌드 경로

### 1차 — 수직 슬라이스

**목표: 캐릭터를 찍어내는 파이프라인이 작동하는지 증명한다.**

- 캐릭터 **2명** — 엑스(버스터), 제로(세이버). 임시 도트로 시작
- 맵 2개, 잡몹 3종, 보스 1
- 아머 파츠 1세트, 레벨업, 스킬 습득 1회
- 키보드 + 터치 입력, Artifact 퍼블리시로 실기 확인

> **성공 기준 ①: 3번째 캐릭터를 데이터 파일 1개 + 스프라이트 시트 1장으로 추가할 수 있는가.**
> **성공 기준 ②: 임시 도트를 진짜 스프라이트로 교체할 때 코드 수정이 필요 없는가.**
> 둘 중 하나라도 실패하면 구조가 틀린 것이며, 로스터를 늘리기 전에 고쳐야 한다.

엑스·제로 2명으로 먼저 규격을 확정하는 이유: 규격이 굳기 전에 7명을 넣으면 규격이 바뀔 때마다 7명분 데이터를 다시 만져야 한다. 2명으로 확정한 뒤 나머지를 일괄 투입하는 편이 **7명 전원에 더 빨리 도달한다.**

### 1.5차 — 에셋 교체 (PC 세션)

- 원작 시트 수집 → `detect_frames.py` → Aseprite 태그 부여 → `assets/sprites/`
- 임시 도트를 실제 X4 스프라이트로 교체
- 이 단계는 PC가 필요하며, 1차와 병행하지 않고 규격이 확정된 뒤에 한다

### 2차 — 로스터 완성

- ✅ 록맨, 블루스, 포르테 투입 (클래식 계열 체형 — X 계열보다 작고 프레임 수도 적다)
- ⬜ 벤트/아일, 제로(제로 시리즈)
- ⬜ 액셀 — 원작에 도트가 없어 스프라이트 에딧이 필요하므로 후순위

캐릭터의 개성은 전부 데이터가 정한다.

| | 이동 | 기본 무기 |
|---|---|---|
| 엑스 | 대시 · 에어대시 · 벽차기 | X 버스터 (차지) |
| 제로 | 대시 · 에어대시 · 벽차기 · 이단점프 | Z 세이버 (차지) |
| 록맨 | **슬라이딩** (대시·벽차기 없음) | 록 버스터 (차지) |
| 블루스 | **슬라이딩** (대시·벽차기 없음) | 프로토 버스터 (고위력·저연사) |
| 포르테 | 대시 · 이단점프 (벽차기 없음) | 포르테 버스터 (저위력·고연사) |

### 3차 — 콘텐츠 확장

- 보스 패턴 템플릿 8~10종 구축
- 시그니처 보스 20~30명 전용 패턴
- 일반 보스·잡몹 데이터 대량 입력 (지속 작업)
- 맵·지역 확장

## 10. 배포

정적 웹앱이므로 별도 서버가 필요 없다. 두 경로를 병행한다.

| 경로 | 용도 | 빌드 | 공개 범위 |
|---|---|---|---|
| **Artifact** | 개발 중 즉시 확인 | 단일 HTML (전 에셋 인라인) | 기본 비공개 |
| **GitHub Pages** | 정식 배포, 고정 URL | 일반 정적 번들 | 공개 |

### 10.1 빌드 구성

- `npm run build` — Pages용 정적 번들. `base: '/rockmanrpg/'` (프로젝트 페이지 경로)
- `npm run build:artifact` — `vite-plugin-singlefile`로 전 에셋을 인라인한 단일 HTML.
  Artifact는 외부 요청이 차단되므로 인라인이 필수다
- 두 빌드 모두 앞단에서 `gen-placeholder` → `validate-data`를 실행한다

### 10.2 GitHub Pages

- `.github/workflows/deploy.yml`이 푸시 시 자동 빌드·배포
- 저장소 Settings → Pages → Source를 **GitHub Actions**로 설정해야 동작한다 (수동, 1회)
- 설정 전까지 워크플로는 아무 일도 하지 않는다. 공개 시점은 나중에 정한다

> Pages 사이트는 저장소를 비공개로 돌려도 **공개로 게시된다.** 또한 무료 플랜에서는 공개 저장소에서만 Pages를 쓸 수 있다. 공개 여부는 게임을 실제로 공개할 시점에 결정한다.

## 12. 에셋 관련 메모

원작 스프라이트는 캡콤의 저작물이다. 팬 제작물로서 실무적 위험은 낮지만, 다음을 지킨다:

- **비상업 유지** — 판매·후원·광고 없음 (위험의 대부분이 여기서 발생)
- 공식 제작물이라 주장하지 않음, 팬 제작 표기
- **코드는 에셋 경로만 안다** — 스프라이트를 커밋하더라도 이 원칙은 유지한다. 나중에 자체 도트로 교체할 때 경로만 바꾸면 되므로 설계상으로도 이득이다
